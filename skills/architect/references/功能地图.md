# 功能地图（第 3 步，✋ 人确认）

项目**唯一的进度表**，也是给人查漏补缺的全貌。

## 骨架（从上往下拆，大类 → 小类 → 细分）

1. **给谁用、解决什么**：目标用户、痛点、我们的解法。
2. **接进来的外部东西**：用了哪几家服务 / 模型 / 平台，每家怎么接、怎么登录、各自的限制。
3. **结构**：用户看到的空间怎么分（比如工作区 / 页面 / 模块），每一块里有什么。
4. **每一块里能做什么**：功能逐条列。**有几种执行者就并排几列**（比如两种不同的模型各自怎么做到这件事），差别一眼能看出来。
5. **协作**：多人 / 多个 agent 一起的部分。
6. **上手**：第一次打开、导入、登录。
7. **发布**：打包、签名、分发。

项目不同，骨架可以增减，但**每一项都要能回答「做到哪了」**。

## 进度标记

✅ 能用　🔨 在做　📝 定了没做　💭 想法　⏸ 暂停　🧪 界面上只有预览

- **立项时进度全空。** 做完一个勾一个。
- 进度必须从工单和代码里核出来，⛔ 不凭印象填。
- 「能用」要写清口径（比如：代码已合进主干，还没打包 ≠ 用户手里有）。

## 和工作流接在一起

- 开单时合同写明「功能地图：是哪一项」。地图上没有这一项 ⇒ 先补进地图（进度空着）再开单。
- **合并复验完，当场回地图改进度。** 走之前的收尾清单里要有这一步。
- 地图顶上盖核实日期和它盯的东西（见 `维护.md`）。

## 写法

- 人话。不出现文件名、接口名。
- 每块能折叠（markdown 里用 `<details><summary>`），人先看大类，关心哪块点开哪块。
- 画完自己先扫一遍，把一眼能看出来的缺口写在给人的消息里——这就是它的用处。
