# 验收与复核（第 10–12 步）

## 实现和审计分开

同一只做实现和审计，要分两个阶段、两个工作区：先在自己的分支实现测试，再换一个干净的工作区对照合同、改动、测试复核。**同一个人做两件事，不等于可以省掉第二遍。** 你给自己做的「复核」都在你自己的推理链里，所以它复核出来的永远是「自洽」。写给别人看，比自己再看一遍便宜得多。

## 合并后自己复验

1. 拉新代码。**依赖变了先装**（不装的话整个测试文件加载失败，条数变少，看起来像「挂了几条」）。
2. 跑全量测试，**读汇总那一行**：条数、失败数。绿是从那一行字读出来的，不是从退出码推出来的。条数突然变少也要追。
3. 读改动：重点看状态归谁、有没有第二个写入者、错误路径。
4. 偶发失败：重跑过了不等于没事。记下测试名；**第二次出现就开单修**（已经真发生了）。

## 验结果不验步骤

- 别核对「我拉过了 / 我重启过了」，去读一次那个改动在不在。脚本说「✅」不代表做成了：拉成功但重启失败、拉失败但重启成功，脚本都可能回「✅」。
- 考「读没读到」只用**被测对象独有**的内容：编一个只有它知道的暗号，让它答出来。用常识就能答对的问题考不出任何东西。

## 确认一件事是真的

- **第一个成立的解释是起点。** 找到它之后往下再追一层，问这个原因自己是从哪来的，追到没有下一层为止。
- **刚逮到别人一个错、心里得意的那一刻，回头查自己刚做的同一件事。**
- **你最信你刚做完的那个动作。** 搜完了不等于核过了，写完了不等于记下了，说出口了不等于办了。
- 「文档写着」和「我实核过」是两句不同的话，不要把它们说成一句。状态、部署、故障，一律只读实核，不照着文档猜。
- 一个瞬时快照（你查的那一下是空闲的）和别人反复撞出来的经验，不是同一种证据。
- 队列里的消息只当「入队时发生过」，不当「当前状态」。冲突时按实时状态，并标明旧消息已过期。
