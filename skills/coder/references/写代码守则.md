# 写代码守则

> 代码鼠和前端共用这一份。拼进岗位说明书时原样放入，⛔ 别在别处再抄。

**范围**
- 只做这张单要的。修 bug 就修 bug，不顺手重构周围、不顺手扩合同、不顺手加配置项。
- 能直接改就直接改。⛔ 不加兼容层、不加开关参数、不给新参数塞默认值兜底；只有一个调用点，就把调用点一起改掉。**兼容层就是第二套真相。**
- 确定没人用的东西就删干净：不留改名成 `_unused` 的变量、不为旧名字再导出一次、不留「这里删掉了 X」的注释。
- 改现有文件优先于新建文件。新建是第二套真相最常见的来源；真要新建，交付说明里说清为什么不能改现有的。

**不打补丁**
- 同一条逻辑先 grep 一共有几份，再动手。四份以上就收成一个函数，让「漏改一处」在结构上不可能。
- 被指出的是一个实例，问题是一个类。驳回点了一处，就把同类的都扫一遍。
- 修在**第一个被违反的边界**上，不修在症状出现的地方。

**设计与结构**
- **SOLID、单一职责**：按变化原因划分职责；只为已确认的扩展需求设置扩展点；替换实现保持接口契约；接口按调用方需要拆分；高层业务依赖稳定契约，底层实现从边界接入。禁止万能类、万能服务或庞大接口混装独立职责。
- **组件化**：按业务能力和依赖划分模块和组件，明确输入、输出和状态归属；跨组件只通过明确接口协作，不绕过接口读写内部状态。失败须让调用方获知，并能按实际运行方式诊断和恢复。
- **设计模式**：现有耦合、变化点或协作关系适合某种模式时才采用，并对应具体问题。抽象、配置、扩展点和新依赖须有已出现的共同变化、明确需求或质量证据；禁止为套模式增加无用层次或框架。
- **一类代码一个文件**：一个类 / 一个协议口 / 一份规则。
- **文件之间不互相引用**：A 引了 B，就不许 B 再引 A。互相引用说明两个文件其实是一个，该拆的是职责，不是文件。

**抽象**
- 先写最小的那一版，等它不够用了再让它长。⛔ 不为想象中的将来做设计。
- 两三行相似的代码，好过一个过早的抽象。一次性的操作不需要辅助函数，一个调用点不需要配置项。

**校验和防御**
- 只在系统边界上校验：外部输入、命令行参数、外部接口。内部代码和框架保证的东西就信它。
- ⛔ 不给不可能发生的情况写错误处理、兜底和防御，那是在给后来的人造迷雾。
- 注意安全：拼命令、拼 SQL、往页面里塞外部内容都要当心注入。发现自己写出了不安全的代码，当场改掉。

**注释**
- 默认不写。只写看代码看不出来的**为什么**：藏着的约束、微妙的不变量、绕开某个具体 bug、会让读的人吃惊的行为。
- ⛔ 不解释代码在做什么，⛔ 不写「给 X 用的」「为 Y 单加的」——这些会随代码演化烂成假路标。来龙去脉写进提交说明和交付说明。
- 别人的注释，除非你删了它描述的代码、或者确定它是错的，否则不删。

**卡住的时候**
- 一个做法失败了，先弄清为什么：读报错、核你的假设，再试一个有针对性的改法。⛔ 不原样重试，也别失败一次就换路。

## 低耦合红线（出现任何一条就不许交）

- 同一个常量 / 名单 / 状态在两处各自维护
- 越过公开接口去读另一个模块的私有存储
- 为一个调用方新增专用字段，却没有稳定的合同
- 兜底悄悄接管，没有日志，也没有退出条件
- 新旧实现同时跑，却没有迁移判据、删除条件和负责人
- 测试只覆盖辅助函数，证明不了生产入口会调用它

要新增兼容层、开关、新旧并行，必须先让人或架构师拍板。**长这个样子的就是**：环境变量分支，或者名字里带 `_v2` / `_new` / `legacy` / `old`。
