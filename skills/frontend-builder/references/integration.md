# 架构与后端衔接：单 agent 执行

同一 agent 负责完成当前目标所需的产品、架构、前后端与验证工作。角色切换用于理清判断和证据，不代表存在等待接单的另一个人；不要求用户安装协作系统或另找后端工程师。

## 先判断是否需要后端

已有服务时先读实际接口与代码并复用；纯本地、无需共享的工具可采用本地存储，不为页面主动加服务器。跨设备共享、多人权限、受保护数据、服务端调用或可靠后台任务等需求，才评估必要的后端。技术选择围绕目标、运行条件和维护能力，使用当前官方资料核实版本相关能力。

缺少服务时先给用户可理解的实现建议和必要取舍。在用户已授权的完整应用范围内，自行实现必要服务/适配器和持久化；不要以“等后端”终止工作。若用户只授权前端或原型，就整理清楚接口需求、保留可替换边界与明确的假数据标记，不擅自扩展成生产服务。

## 固定最小契约，再让两端遵守

只记录本轮需要的约定，可放在已有规格、类型或接口文档中：

| 约定 | 要解决的问题 |
| --- | --- |
| 数据与所有者 | 谁提供真相、稳定身份/版本、哪些是临时草稿、哪些要持久化及共享 |
| 读写与权限 | 输入/输出、调用者身份、权限范围、错误含义、允许的资源来源 |
| 列表与实时 | 排序/分页游标、增量与最终事件、重连补读、去重和旧请求保护 |
| 修改与恢复 | 重复提交、取消、冲突、失败重试；哪些动作需幂等或事务 |
| 文件与配置 | 附件类型/限额/鉴权读取、敏感配置保存位置、旧数据兼容 |

先定义服务端权威状态与错误，再接界面。前端不得用另一个本地状态库伪装跨设备审批/确认等共享事实。前后端由同一人写，也不能用互相迁就的假件替代真实契约验证。

## 实现必要服务并验证真实链路

- 选择足够小、可维护的结构，配置集中管理；依赖、启动步骤和存储方式可复现。不要从需求中的一个按钮推导出无关基础设施工程。
- 需要保存的数据跨实际重开后仍应存在；多步写入、并发和迁移按风险选择事务或恢复方案。不能用进程内数组冒充持久化。
- 对受保护资源在服务端验证身份与权限，校验输入、路径和资源来源；前端隐藏按钮不构成权限控制。错误要稳定且能被界面理解，不泄露凭证或内部敏感信息。
- 凭证采用目标平台合适的安全存储与受控调用路径，禁止将服务端长期秘密打包进公开前端。用户账号、支付、商店发布等操作按实际授权处理，不向用户索要可由安全配置入口直接保存的秘密正文。
- 联调实际入口、服务和存储，覆盖核心路径与高风险失败场景。假件证明组件行为，真实运行证明接线；分别记录。

## 从实现切换到复核

实现一段后，重新按用户目标和契约读 diff，优先查状态归属、权限、异步竞态、失败恢复、兼容与回退，再补能覆盖缺口的验证。明确这是同一 agent 的自查，不宣称独立审核；宿主若另有审核流程照常遵守。

发现可修复问题就在授权范围内修复并更新证据，直到达到本轮交付要求。真正需要用户处理的外部条件应精确指出，同时继续不受影响的工作。不要为例行岗位切换新建 agent、发外部消息或反复请求许可。
