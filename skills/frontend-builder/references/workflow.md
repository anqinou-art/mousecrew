# 完整工作流：主动设计并交付前端

适用于从想法做新界面、整体改版或需要补齐设计的任务。局部修复从相关阶段进入，复用已有决定。以下描述输入、判断、产物与继续条件，不额外设立固定审批关卡。

## 1. 理解目标，形成首版建议

输入可以只是一句话、几张图或现有产品。先确定用户要在哪种情境下完成哪件事、目标设备、已有系统与限制。按 [需求采集](requirements.md) 找缺项，避免把框架名、颜色值和控件位置变成用户必答题。

默认主动开启分轮对话：设备/使用方式、功能/页面、风格/参考。解释 PWA、原生手机 App、跨平台手机方案与 Electron 等名字时，围绕用户体验、安装使用和维护取舍给推荐；使用需求采集中的话术，由执行者提出技术组合与推荐理由。

主动提出第一版范围、默认做法和暂缓项，解释取舍。例如单对象日常聊天可推荐默认回到上次会话；多对象管理则可能以列表为入口。根据使用任务给理由，不把某一种导航固化成通用模板。

产物是一小段可修改的目标说明，优先放在项目已有规格中；没有现成规格时保存一份简短的项目说明。核心任务和约束足够清楚后继续；仍有关键目标歧义时问该问题，其余独立工作可以推进。保留假设标记，不把推测写成用户要求。

## 2. 设计页面结构与操作路径

从任务推导页面，而不是先决定要几个 Tab。明确各页承担什么、入口在哪里、做完去哪里，以及中断后如何继续。移动、桌面的导航可以不同，任务语义保持一致。

选最重要的一条路径做低成本可点原型：从进入到完成，包括返回和必要的失败恢复。粗原型先回答“会不会用、绕不绕路”，不用提前填满所有装饰和次要页面。拿原型请用户做具体任务，如“找回昨天那张图片”，比只问“你觉得怎么样”更能定位问题。

路径已清楚、明显死路已消除，就可深入视觉与接线。技术难点可以在此时小范围验证。若反馈暴露页面职责或导航问题，先调整结构，不能只换颜色掩盖。

## 3. 提出视觉方向，完成一个代表页

已有设计时先归纳现行规则；没有设计时根据产品气质、使用环境、内容密度和用户偏好提出方向。参考来自用户素材或合适的公开案例，区分参考灵感与可直接使用的资产。

用户可以给多张图分别表达喜欢的配色、组件或图标；标明每张借鉴哪一部分。主动帮用户整理喜欢的图标/素材，先搭配在一个代表页中查看。几张图之间冲突时给协调建议，不把每种风格都硬拼进页面。

方向不确定时做少量有明显区别的方案，说明布局、字体、色彩、空间感各自如何服务任务，并给出推荐。不要只提供同一界面的几种换色，也不要用大段风格形容词代替可查看的样张。

挑核心页面放入真实长度的标题、消息或卡片，处理主次、留白、字体角色和主要动作；需要贴图就接 [资产工作流](visual-assets.md)。用户表达“更像自己的房间”时，把反馈转换成具体的页面组织和视觉变化，展示修改，不追问每个像素。

当方向足够明确，把已采用的规则写回现有设计文档/常量：颜色角色、字体层级、间距节奏、圆角/边框、图标语言与素材用法。用户明确没定或要求暂缓的部分继续标记；普通技术细节不逐项请示。

### 把认可的样页记成设计配方

主动建议用户在铺开页面前定下主要配色与图标风格。执行者负责把样页转换成下面这些可复用规则，优先更新项目已有设计文档与共享常量，不让用户填参数表，不在多个文件维护互相冲突的值。

| 配方内容 | 执行者要记录到能复用的程度 |
| --- | --- |
| 采用依据 | 哪个代表页/版本体现当前方向；用户明确认可了什么、哪些仍未定；参考图各借鉴什么 |
| 色彩角色 | 主色、页面/卡片背景、文字、边框及必要状态色的值与用途；不能只记几个没有用途的色号 |
| 字体层级 | 标题、正文、辅助文字的字体/字重/尺寸关系，字体来源与缺失时的回退 |
| 图标语言 | 选定的图标家族或同套素材、线条/填充风格、尺寸和颜色规则，选中/禁用等必要状态 |
| 组件样式 | 按钮、输入框、卡片、菜单等已有组件的间距、圆角、边框/阴影和状态；记录实现入口 |
| 图片装饰 | 原件与派生件、使用组件、锚点/裁切/伸缩规则；指向资产清单，避免重复复制来源信息 |
| 多端适配 | 小屏、桌面、键盘与长内容时的布局变化；共享视觉语言，保留必要的平台交互差异 |

完成后以配方作为后续每页的默认依据，复用同一组件/样式来源。新页面需要新组件时从现有语言推导；若引入新的主色或整套图标等明显方向变化，先解释必要性、拿样例讨论，再更新配方与受影响页面。用户没有明确认可时不能擅自标为定稿，也不为普通尺寸调整重复走一轮风格确认。

## 4. 把代表页展开为可实现的系统

识别会重复出现的组件，先复用现有库；为必要状态建立可查看的例子。可用组件预览、原生 Preview 或轻量展示页，不强制某个工具。只建本任务会用到的规则，避免先造一个庞大设计系统。

按风险补齐状态：加载、空、忙、错误、禁用、选中，以及长内容、图片失效、键盘出现、窗口收窄等。组件外观和行为要同步；灰掉的按钮仍需明确为何不可用，失败后应能继续。

明确数据来源、权限、持久化、实时事件、取消与恢复、重复提交和兼容边界。按 [接口与协作](integration.md) 处理缺口；不要让用户逐字段设计，也不要用假成功或第二份状态库掩盖缺失能力。

可在项目文档用一张短表记录复杂点，简单任务不必额外建表：

| 组件/动作 | 输入与状态来源 | 用户动作 | 失败/恢复 | 持久化归属 |
| --- | --- | --- | --- | --- |
| 附件待发区（示例） | 当前会话草稿、选取的文件 | 预览/移除/发送 | 失败保留本次草稿，不串会话 | 本地草稿按产品约定，发送后的消息由服务端保存 |

状态、依赖和恢复方式足够明确即可实施；无法接真的部分保留明确边界，并推进不依赖它的工作。

## 5. 贯通核心链路，再扩展

先让一个主要任务在实际入口完成，如进入会话→输入→发送→看到回复→重新进入能读到记录，然后基于共用组件扩大覆盖。具体顺序以风险和已有系统为准，不要求每次重造聊天链路。

组件假件帮助验证状态，真实接口验证接线，设备现场验证平台行为；各自证明的结论分开。详细工程经验按需读 [实现配方](implementation.md)。交付证据按 [验收与交付](delivery.md) 组织。保留已有风格、数据与设置，避免并行改动覆盖同伴在制品。

## 6. 自行检查质量，再收体验反馈

对照目标、代表页和实际运行结果，先处理执行者可以判断的问题：

- 信息与操作：主次清晰，主要入口可发现，反馈及时，错误后知道怎样继续。
- 视觉与内容：字体/图标/组件一致，长内容不挤坏布局，贴图不变形、不遮文字、不挡点击；空状态也有完整排版。
- 设备与可读性：相关尺寸、安全区、键盘、焦点、文字缩放与对比度适合使用；平台可访问性要求按实际目标落实。
- 行为与性能：滚动、输入、图片加载顺畅；高风险的鉴权、上传、竞态、取消与恢复有针对性证据。

按改动风险选择检查，不机械遍历所有按钮和设备。用户设备体验集中在代表性任务和主观感受；工具检查不能证明完整可访问性，AI 自查也不能冒充真实用户访谈。

把反馈对应到原因：入口难找回到结构，整体太像办公工具回到视觉方向，发不出去回到接线，单个控件裁切则局部修。修正相应规则或组件，避免只打散落补丁。已验证且没变化的部分不用重跑。

## 7. 交付一个可接手的结果

交付可打开的实际入口和准确运行方式，核实它能载入。把源码、配置入口、资产来源与派生关系、相关构建/安装步骤、关键验证和已知限制放在项目既有文档，做到接手者不用翻聊天。

声明当前交付层级：交互原型、接真候选、设备可用版本或已发布版本。原型只有有限数据/状态时说清楚，不能把生产所需鉴权、性能与恢复能力默认视为已经具备。

若本次包含构建/安装，按授权完成对应产物与运行验证；发布、商店提交、付费或重启等遵循实际授权与项目流程。没有授权的动作写成具体后续事项，不阻断已授权的其他交付。

## 方法依据

流程按前端交付用途归纳，不是强制行业标准。可进一步参考 [Design Council 的 Double Diamond](https://www.designcouncil.org.uk/resources/the-double-diamond/) 理解探索与收敛，[GOV.UK 原型方法](https://www.gov.uk/service-manual/design/making-prototypes) 选择原型深度，[Storybook 状态示例](https://storybook.js.org/docs/writing-stories) 组织组件预览，以及 [W3C WAI 评价方法](https://www.w3.org/WAI/test-evaluate/) 理解工具与人工评价的边界。采用方法不意味着必须安装其工具或照搬其产品风格。
