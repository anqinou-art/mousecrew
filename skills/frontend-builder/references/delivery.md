# 验收与交付

## 以用户拿到后能用为完成标准

先核对本轮承诺的是原型、接真候选、可安装版本还是上线版本。只做到样稿时交代假数据和未接能力，不能把它当作完整产品；若用户授权了完整实现，就继续完成其必要的构建、接线和交付，不停在截图或代码片段。

维护一份与本轮范围相称的简短验收记录，可复用已有项目文档：

| 用户任务/风险 | 检查方式 | 结果与证据 | 未验原因或剩余动作 |
| --- | --- | --- | --- |
| 示例：选图后无文字发送 | 组件检查草稿/失败保留，真实链路核附件到达和历史显示 | 按实际运行填写，不提前写通过 | 没有模型凭证时，明确只验到服务端或本地假件 |

## 选择有信息量的验证

- 视觉布局变化：查看代表性视口/设备的实际画面，核层级、字体、比例、裁切、溢出及长内容。不是每次都必须两端全测。
- 行为与数据变化：选与改动有关的构建、组件、接口或集成检查，重点覆盖状态切换、重复提交、失败恢复与数据归属。已有有效证据可复用；输入、代码、环境未变时不重复同义检查。
- 原生权限、WebView、Keychain、通知、签名或安装：在能代表目标的运行环境验证。编译通过、隔离假件、无签名包、模拟器各有边界，不能相互替代。
- 可读性与可访问性：检查必要的对比度、文本缩放、键盘/焦点、语义名称和命中区域；自动工具不能单独证明完整合规。
- 高风险链路需针对性验证；常规按钮体验可集中给用户做代表性任务，不机械逐个代点。缺设备/凭证写清未验，继续可完成的部分。
- 工具不具备截图/图像理解/设备控制等能力时，不虚构已看图或已实测。使用现有替代证据，并说明缺口；只在确有必要时请用户提供关键反馈。

GUI 操作遵守可用工具的操作规则，优先当前可访问性状态与元素定位；界面变化后刷新状态，坐标必须来自当前画面。重要动作读回结果，工具返回成功不等于产品状态已经成立。只查看当前任务有关的页面/窗口。

## 一次可接手的交付

按实际交付层级，提供下列必要内容；优先更新已有文档，不机械增加文件：

| 内容 | 用户或下一位维护者应能知道什么 |
| --- | --- |
| 可用入口 | 打开什么、如何启动、是否是假数据、需要哪些运行条件 |
| 源码和构建 | 本轮版本/修改范围、依赖与锁文件、构建或安装方法、必要的平台差异 |
| 配置 | 环境变量/本地设置的含义和取得方式，只有占位示例，不附真实凭证 |
| 设计与资产 | 采用的设计配方、组件入口、原件/派生件、来源与许可、无法还原的部分 |
| 数据与恢复 | 数据保存位置与作用域、升级兼容、必要时的备份/回退方法；没有验证过的恢复不宣称可用 |
| 验收与限制 | 有价值的通过证据、未验平台/路径、已知缺口与下一步 |

用户说“打开给我看”时，优先打开当前可用成品或可交互预览，核实载入。只有截图时直接说明，不能用图片画廊冒充运行中的 App。

审阅本任务 diff，只纳入本任务文件，不覆盖或整仓提交其他人的在制品。是否提交/推送/合并按授权与项目流程执行。对外发布、付费、账号操作、破坏性数据动作和日用服务重启不由交付文档自动授权。

## 完成与继续

核心承诺已实现、必要检查通过、入口可用、证据和限制清楚，才报告对应层级完成。遇到外部条件阻塞时指出精确缺项、影响的功能和谁能解除；不要笼统把整个项目标为不可做。

用户反馈入口难找就回到结构，整体气质不对就回到代表页和设计配方，数据错误回到状态/契约，局部裁切则修相关组件。更新同一份现行配方和文档，避免旧方案继续指导新页。用户变更范围时同步记录，不把新增需求默认为原验收失败。
