# 前端需求采集

用以下方法与用户共同形成方案。先从项目现有资料中填好答案，只问影响当前选择的未知项。

## 从整体到当前页面

先从已有上下文填好答案，再问会改变这次实现的缺项。下表用于执行者形成判断和方案，不是发给用户逐项填写的问卷。对普通布局、组件位置和状态处理先给推荐；只把涉及目标、偏好、重要取舍或无法推断的约束交用户回答。讨论阶段可以给可撤回的小样；已明确授权的局部改动直接完成。每次集中问少量相关问题，给默认建议及其后果，允许用户说“不知道”。

| 层次 | 要知道什么 | 怎么落地 |
| --- | --- | --- |
| 使用条件 | 用什么设备、在哪里使用、是否已有 App/后端、上线与维护约束 | 执行者据此选技术栈；已有项目优先沿用，不强迫用户在不熟悉的框架名之间选 |
| 产品定义 | 给谁用、主要做什么、第一版最需要哪几件事 | 明确本轮范围和暂缓项 |
| 整体布局 | 页面/Tab 分工、主要入口、参考图、配色与字体角色 | 形成足够实现的布局；布局未定时不要铺满全部页面 |
| 视觉素材 | 风格描述、已有成图/素材包、必须保留或不能改的内容 | 执行者整理资产与相对布局；缺素材按 [资产流程](visual-assets.md) 提方案，不要求逐张坐标标注 |
| 逐页细化 | 页面任务、数据来源、可执行动作和回退路径 | 只展开这次涉及的页面 |
| 交互细节 | 点击/长按/滑动、键盘、加载/空/失败、过渡 | 用实际失败场景补齐，避免只有正常态 |

账号接入、服务运行位置、数据存储与预算会影响整体方案。先解释实际体验和维护代价，再在当前授权内完成必要的架构决定与实现；具体做法见 [架构与后端衔接](integration.md)。

## 默认的分轮需求沟通

下列是可选话术与配合方式。按已有答案跳过已知项，每次聊当前需要的一小组，不一次发完长问卷。用户明确选了技术或已经有项目时尊重该选择。

### 先聊设备，再解释方案

开场可以问：“主要想在手机上用、电脑上用，还是两边都用？手机是苹果还是安卓，电脑是 Windows 还是 Mac？只给自己用，还是还想分享给其他人？”只补影响范围的未知项。

接着问使用方式：“希望像一个安装好的 App 点开，还是打开网页就能用也可以？”据此筛选并解释合适的方案；用户提到 PWA、iOS、安卓或 Electron 时接住并说明区别，不避开其明确问题。无需把下表完整塞给每位用户。

| 用户会听到的名字 | 怎么解释 | 执行者要核实的取舍 |
| --- | --- | --- |
| 网页 / PWA | 浏览器能打开；支持时还能添加到主屏幕，像 App 一样进入 | 安装、推送、离线与设备功能在各系统/浏览器的支持不同，不能一概保证 |
| iOS App | 给 iPhone/iPad 使用的安装应用 | 开发/签名/分发条件、目标设备能力；费用和发布要求按采用时的现行规则核实 |
| Android App | 给安卓手机/平板使用的安装应用 | 安装与分发方式、目标设备差异和所需能力 |
| 跨平台手机方案 | 可以共享不少代码，分别做苹果和安卓 App | 两边仍需各自构建、权限适配与设备验证，不承诺写一次就完全相同 |
| Electron 桌面 App | 用网页界面技术制作可安装的电脑应用，面向 Windows、macOS、Linux | 属于桌面三平台；手机需另选方案。各平台仍需构建/打包和验证，并考虑资源占用与系统集成 |

目标设备、交付方式和技术实现是相互关联的不同维度。“手机电脑都要”不直接等于 Electron，也不强行只选一种技术。由执行者结合功能、维护能力和已有项目推荐组合，用体验和成本解释理由；只对会影响当前选择的要求继续提问。

### 再聊功能，主动建议分页

可以问：“最想拿它做哪几件事？第一版哪件最重要？有没有想单独做成一页的功能？”用户只说想聊天也足以继续，不要求先交功能清单。

把愿望整理成可讨论的页面建议，例如“聊天是主页面，历史入口放侧边，外观和连接配置集中到设置，这样日常少跳转”。解释每页用途，问是否符合习惯；页数与导航由任务推导，不把这个例子当所有产品模板。用户已有分页想法就沿着它讨论。

### 通过参考图和素材理解喜好

主动邀请用户给几张喜欢的参考图，也可以是不同产品里的局部：“这一张喜欢配色，那一张喜欢按钮，另一张喜欢图标，都可以。”分清用户喜欢的是颜色、排版、组件形状还是整体氛围，不默认要求整张复制。

可以一起挑喜欢的图标、贴纸、背景或字体。用户没收藏也没关系，执行者可在任务允许范围内寻找或提出候选，并说明推荐；素材获取与使用依据按 [资产流程](visual-assets.md) 处理。参考图不是开工门槛，已有素材也无需用户先整理和标注位置。

### 先搭一页，再定配方和铺页

执行者选能代表主要界面的那一页，将拟采用的配色、字体、图标、素材和组件真正组合起来。用接近实际的内容，给可打开的样页；看样时问容易回答的具体问题，例如“这页的颜色和图标像你想要的吗？更喜欢轻一点还是更有装饰感？”

收到反馈后主动调整，并建议把已认可的主要配色、图标风格和组件规则记成 [设计配方](workflow.md)。用户看实际效果和主要选择，普通尺寸与实现参数由执行者整理。方向尚未确定时继续小范围看样；确定后其余页面沿用同一配方，避免逐页重新选风格。以后用户改变方向，更新配方并说明关联页面影响。

## 按产品选择页面细节

下面的联系人、聊天和面板是可选案例，不是默认功能清单。内容站、预约工具、作品集或管理系统同样沿用前面的工作流，再按自己的核心任务展开：

- 内容/展示页：用户先看到什么，如何到达详情或主要行动；内容从哪里来，是否需要搜索、分享或搜索引擎收录。
- 列表/详情页：条目关键字段、排序筛选、分页、空结果、返回时的位置，以及新增/修改的实际需求。
- 表单/办事页：哪些字段必要、错误在哪里解释、何时保存、提交后怎样确认，以及中断或重复提交如何处理。

只展开本轮需要的页面；账户、聊天、通知、支付或后台管理均不因案例出现就自动加入。

## 联系人列表

- 明确哪些人/会话显示在这里，卡片需要名字、头像、最近消息、时间中的哪些信息。
- 增加、删除、置顶、归档分别有无需求、语义是什么；手机左滑只是可选建议，桌面可用菜单，不混淆归档和删除。
- 搜索是全局聊天还是当前列表筛选；文字、图片、文件、链接覆盖到哪一步。不要放一个无实际能力的搜索框。
- 用户能否改背景、卡片色、头像，入口在哪；颜色可提供调色板和色号输入，设置按约定范围持久化。

## 聊天页面

| 部分 | 需要明确的体验 |
| --- | --- |
| 导航与布局 | 进入聊天后主 Tab 是否收起（可建议收起，按导航习惯决定）；如何回列表；头像/名字/时间是否展示 |
| 消息与滚动 | 打开时看最新；新消息如何到达；上翻旧记录时怎样保留位置；回到底部入口 |
| 搜索 | 当前会话还是全局，类型与条数上限/分页；结果能否跳到那条消息 |
| 输入 | 多行换行、发送/换行键约定、长度限制、发送与停止状态、切会话草稿 |
| 附件 | 图片/文件支持范围、选取/粘贴/拖拽入口、待发预览/移除、说明、是否允许只发附件 |
| 图片显示 | 气泡内缩略显示，查看大图；原图上传策略与显示缩放分别决定 |
| 菜单 | 只放本产品需要的角色设定、连接配置、上下文管理或其他功能；不能自动全部添加 |
| 自定义外观 | 背景/气泡/头像各自能否改，私聊和群聊的作用域是否独立，重启是否保留 |

图片说明作为附件发送体验的一部分考虑，可复用主输入区；不必多造一个输入框。图片编辑器只有需要时才问裁剪、旋转等功能，参考图可用用户素材或适合的设计工具，不强制额外生图。

## 控制面板与设置

这两类页面由实际任务决定，不预置一套所有产品必须采用的布局。主动给出合理分组，重点确认：

- 面板：用户打开来要做哪件事，哪些是状态、哪些是动作，详情从哪里进入；不要顺手堆满监控图。
- 设置：哪些改动即时生效、哪些需要保存，影响当前会话/整台设备/整个账号中的哪一层；失败是否保留输入，敏感值如何安全保存。

## 基本体验要求

以下只适用于产品实际包含的相应能力；不因此新增自定义主题、消息或搜索。

1. 自定义风格持久化，刷新或重启后仍在。
2. 背景图适应容器，不挤走其他控件。
3. 搜索与大量记录要考虑性能，按数据规模选分页、索引或虚拟列表。
4. 消息有底部锚点与回底入口；后续实现时区分“正在看最新”和“正在读旧消息”，避免无条件拉回底部。
5. 图片在气泡内缩略显示，不撑爆布局；这不等于强制有损改写原图。
6. 输入框自动换行，同时处理键盘与可用高度。
